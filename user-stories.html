HOW TO READ

故事、驗收、實作，各司其職。

01 / 一則故事，一個可辨認的價值

作為某個角色，我希望完成一件事，以便獲得某個價值。故事是需求討論的起點，會經過團隊對話與驗收範例補充；它不是完整的技術設計。

02 / Given → When → Then

Given · 前提
描述已存在的情境與資料。
When · 行為
描述使用者或外部事件的觸發。
Then · 結果
描述能觀察、能判斷的預期結果。

每則包含正常、例外與邊界情境。「逐步閱讀」只輔助解說，沒有執行測試。

03 / 使用 INVEST 檢查可討論性

盡量獨立、可協商、有價值、可估算、足夠小、可測試。依賴和疑問保留在故事旁，避免在資料不足時宣稱已可估點或可直接開發。若一則超出團隊迭代容量，估算時再拆成可驗收的價值增量。

04 / 本稿的共通規則

  • 全部是需求討論稿；Must／Should 為建議，實作與驗收狀態尚未確認。
  • 四組目標對象依需求分群，同一人可跨組；eSIM 購買是希望促成的轉換行為，訂單資格則屬於福利的前提條件。
  • 排程、共編與購買分開；生成個人回憶圖由符合資格的本趟 eSIM 訂單解鎖。
  • 3 張作品、4 種風格等數字是 Mock 範例，正式額度、期限、退款規則待決。
  • 模型理解偏好並生成內容；路線限制、價格、權益與額度以資料和規則檢查。
  • 生成、下載、點擊分享不等於已公開發文；新行程、App 使用和訂單分別量測。

05 / 進入開發與完成驗收

開發前：釐清關鍵問題、補齊資料與依賴、確認情境與估算。完成時：依故事驗收、處理例外、保留結果證據，並符合團隊共同的 Definition of Done。以下清單不自動等同測試通過。
